# 质检与复审（三关 + 换视角复审）

> 核心事实：**同一个上下文里自审，会给自己盖章。** 写出那句话的推理，正是要用来挑错的那套推理。
> 所以质检必须分三层：机械自查 → **干净上下文的换视角复审** → 用户终审。

## 一、三关结构

```
G1 自查（机械）       → 跑 44-自检清单.md A/B/C，不评分，逐项打勾
      ↓ 全勾
G2 换视角复审（对抗） → 4 个视角独立审，各打分 + 列问题 → 去重 → 逐条反驳 → 只留确认项
      ↓ 通过质量门
G3 用户终审           → 用户看成品与复审结论，拍板
```

**为什么 G2 必须换上下文**：如果 AI 一边写一边审，它会记得"我这么写是有道理的"，于是判定合理。复审者只能看到**成品**，不能看到创作过程、草稿、之前的讨论。

## 二、G2 四个复审视角

每个视角**只看成品**，按"我发现的问题"输出，不负责修改。

### 视角 1：HR 六秒扫描官

- 设定：校招季日均看 200-500 份简历，每份 6-10 秒
- 只回答三件事：① 6 秒内我判断这人能解决什么问题？② 哪一行让我想直接划走？③ 前 1/3 有没有钩子？
- 输出：`{位置, 问题, 严重度(P0/P1/P2), 证据}`
- 典型 P0：首屏全是职责罗列、看不出岗位匹配、有明显错别字

### 视角 2：ATS 解析器

- 设定：只做文本匹配，不懂语义
- 检查：纯文本化后结构是否可解析、JD 关键词命中率、关键信息是否落在图片/表格/页眉页脚里
- 输出：命中关键词清单 + 缺失关键词清单（对照 JD 必须项）+ 解析风险点

### 视角 3：压力面面试官

- 设定：天然怀疑"团队成果"与"漂亮数字"，会拆"我们"→"你"
- 只回答：**哪 3 条最可能被追问到崩？** 追问链写到第 3 层（事实 → 贡献边界 → 数字口径）；此处「第 3 层」对应 `21-出题规则.md` §四五层追问链（L1 事实 / L2 贡献边界 / L3 方法 / L4 数字口径 / L5 边界反例）的第 3 环，两处层号已对齐。
- 输出：3 条高危表述 + 每条的追问路径 + 崩点在哪
- 这条视角专门防"美化过头"——简历写得越漂亮，这里越容易炸

### 视角 4：首次读者（跨域投递必开）

- 设定：完全不懂你原行业，但聪明
- 只回答：哪一句我读不懂？哪个术语我不知道？我在第几行放弃阅读？
- 用于跨域投递（如内容运营投实业、技术投销售），专治"行业黑话"

## 三、质量门与循环上限

| 项 | standard（默认） | strict | off |
|---|---|---|---|
| 复审视角 | 1+2+3 | 1+2+3+4 | 不跑 G2 |
| 通过门槛 | 各视角 ≥8/10 | 各视角 ≥9/10 | — |
| 最多复审轮数 | 2 | 3 | — |
| 每轮结束 | 修完重审，直到过门或到上限 | 同左 | — |

- **评分必须有理由**：扣分点要指向具体行，不能"整体感觉一般"。
- **到上限仍未过门**：停止循环，把「未解决的问题清单 + 卡在哪」如实交给用户，不要假装通过。
- **连续两轮同分**：说明 worker 改不动了（可能是素材不够或规则冲突）→ 升级：把冲突点交给用户拍板，别空转。

## 四、去重与反驳（防假阳性）

多视角一定会互相重复、也一定会误报。两道工序：

1. **去重**：同一处问题被两个视角都提到 → 合并成一条，标注"多视角确认"（权重更高）。
2. **逐条反驳**：对每条确认前的问题，问一句「这条真的成立吗？」
   - 反驳依据必须指向成品原文或 JD 原文
   - **拿不准 = 判定不成立**（宁可漏报，不要制造无效返工）
   - 通过反驳的才进修改清单

> 这一步很关键：不复驳的多视角审查，会把 4 个视角的误报叠加成 4 倍噪音，用户会烦到关掉整个流程。

## 五、执行方式（按环境选择）

| 环境 | G2 怎么做 |
|---|---|
| 支持子代理 | 每个视角起一个独立子代理，**prompt 里只放成品 + JD + 岗位类型**，不放草稿、不放修改说明、不放你的判断 |
| 不支持子代理 | 新开对话，粘贴成品 + JD，让新会话按视角审；或在本会话内显式声明"你现在只知道以下成品"，并禁止回看创作过程 |
| 都没有 | 降级为 `off`，只跑 G1，并在交付时告诉用户"未做换视角复审" |

**给复审者的输入只能有三样**：成品、JD、岗位类型。多给一样，复审就带上了作者的偏见。

## 六、复审结论怎么交付

给用户一张表，而不是一段话：

| 视角 | 分数 | P0 | P1 | 已反驳掉（不成立） |
|---|---|---|---|---|
| HR 六秒 | 7/10 | 2 | 3 | 2 |
| ATS | 9/10 | 0 | 1 | 1 |
| 压力面 | 6/10 | 3 | 2 | 0 |

后接「必改清单」（只列通过反驳的），每条写：改哪、为什么、改成什么方向。
**不要**把没通过反驳的误报列进去充数。

**复审结论要落盘**：存 `[定制]\复审_公司_岗位_YYYYMMDD.md`，含上表 + 必改清单 + 每轮的分数变化。
作用有两个：① 用户能看出"这份简历被挑了几轮、改了什么"；② 下次同岗位再投，能直接从上次的未解决项接着改，不用重跑一遍。

## 七、与主流程的衔接

- **S2 定制**：G1 → G2 → 修 → G3 用户确认 → 才落盘。落盘前不过门 = 不许交付。
- **S4 情报/题库**：只跑 G1（44 清单）+ 情报自身的 URL/置信度校验，不跑四视角。
- **S5 复盘报告**：G1 用 `23-复盘规则.md` 自带的检查，不套用本文件。
- **S6 回写**：逐条用户确认即可，无需复审。

## 八、常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 让作者自己"再检查一遍" | 自我盖章，问题一个都挑不出 | 换视角、换上下文 |
| 把草稿/修改说明给复审者 | 复审被作者的推理带跑 | 只给成品 |
| 4 个视角的问题全列给用户 | 误报叠加，用户崩溃 | 去重 + 反驳 |
| 一直循环到完美 | 永远交付不了 | 设上限，到限如实上报 |
| 复审者顺手改了 | 改和审混一起，无人复核 | 复审只提问题，改由 worker 做 |
